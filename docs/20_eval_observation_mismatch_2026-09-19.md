# 20 · 评测相机不是录制相机：0/18 的根因 (2026-09-19)

本文档取代 `docs/18` 第 7、9 节对失败原因的解释。`docs/18` 修掉的三个评测缺陷都是真的，
但都不是主因。

> **本文档第一版是错的，已重写。** 第一版把原因写成"采集侧的拒绝采样消耗了随机流，
> 导致背景纹理抽取错位"，并据此实现了"把外观钉定到 episode seed"的修复。那个机制
> 站不住：`_base_task.py:60` 在纹理与光照抽取之前就执行了
> `np.random.seed(kwags.get("seed", 0))`，而评测传入的 seed 与记录的 `episode_seed`
> 一致（都是 10000002），所以进入那段之前消耗多少随机流都无关。基于错误结论做的
> 那个修复实测让像素差从 16.3 升到 37.1（它抽到了一张录制时根本不存在的桌面纹理），
> 已经连同其测试一并撤销。错误的来源是：只盯着"平均像素差 16.3"这个标量做推理，
> 没有去看图像本身。看一眼就能发现相机根本不在同一个位置。

## 根因

数据集用**固定相机**采集，评测用**随机采样的相机**。

| | 采集时（记录在 episode 里） | 评测时（`..._v2_pilot.yml`） |
|---|---|---|
| `pose_mode` | `fixed` | 无此键 → 随机采样 |
| `fixed_azimuth_deg` | 90.0 | — |
| `fixed_height_above_table_m` | 0.6 | — |
| `fixed_horizontal_distance_m` | 0.55 | — |
| `fixed_look_at_xyz_m` | [0.0013, −0.0929, 0.8851] | — |
| `target_xy_jitter_m` | 0.0 | **0.06** |
| `minimum_horizontal_distance_m` | 0.55 | 0.65 |

实测 head_camera 位置：录制 `[0.0013, 0.4571, 1.34]`，评测 `[0.3742, 0.7184, 1.4788]`
——**相差 47.6 cm，forward 的 Y 分量正负相反**，即从桌子另一侧看过去。

数据集名字就叫 `fixedcam`。相机配置被完整记录在 episode 里，只是没有任何消费端读它。
这与当年"seed 不能标识场景、必须读 `realized_geometry`"是同一类缺陷：
**产物记录了实际值，消费端却从命令行给的配置重新推导。**

## 证据

单条轨迹过拟合模型（episode 2，31500 步，最好 val loss 0.0166 @ step 27000），
同一状态、只换图像来源：

| 图像来源 | 首步偏离 | 整块动作中位偏离 |
|---|---|---|
| 随机相机渲染（评测原状） | 850.3 mrad | 187.2 mrad |
| **记录相机渲染** | 21.3 mrad | **3.9 mrad** |
| 录制训练帧（上限） | 7.3 mrad | 2.7 mrad |

相机复原后，渲染帧上的预测精度几乎追平训练帧本身。

模型本身没有问题：沿整条 1037 步轨迹取 20 帧，喂录制帧，动作块中位偏离的中位是
**3.8 mrad**，最差帧 66.2 mrad（step 884，释放/插入附近）。它把整条轨迹背下来了。

## 修复

`packages/panthera_sim/dataset.py` 新增 `Dataset.camera()` 与 `Dataset.camera_pose()`，
通过访问层暴露录制的相机配置与实际位姿。

`packages/panthera_sim/robotwin_env.py`：

- `bind_scenes(args, scenes_path, camera)` 现在同时绑定场景表与相机
- `build_task(..., *, camera, camera_pose)` 两个参数**关键字必填、无默认值**——
  有默认值就等于允许静默回落到配置文件的相机，那正是要堵的缺陷
- 相机位姿像几何一样校验，超过 `CAMERA_TOLERANCE_M = 1e-4` 硬失败

修复后实测相机误差 **3.4e-8 米**。

## 第二处观测不一致：通道顺序

相机修好后仍有 7.0/255 的残差，来源是红蓝两个通道对调。

RoboTwin 的采集走 `envs/utils/pkl2hdf5.py` 的 `cv2.imencode(".jpg", rgb)`，而 cv2 把输入
当作 BGR，所以存下来的 JPEG 里红蓝是反的。上游自己是自洽的：它的读取器
`envs/utils/parse_hdf5.py` 用 `cv2.imdecode` 解，来回抵消。

我们的 `panthera_rlds.py` 把字节透传给 TFDS，TFDS 用 `decode_jpeg` 按普通 RGB 解——
**另一个约定**。于是训练看到的圆柱和插槽是青色，而渲染器画出来是黄色，也就是指令里
说的那个颜色。实测 episode 2 第 0 帧：

| 解码方式 | 通道均值 | 与渲染帧的差 |
|---|---|---|
| TFDS 实际给训练的 | [187.0, 210.2, 199.2] | — |
| PIL 按 RGB 解 | [188.1, 210.2, 200.0] | 7.01 |
| cv2 解（上游约定） | [200.0, 210.2, 188.1] | 2.70 |
| 渲染帧（真 RGB） | [198.7, 211.7, 191.7] | 0 |

TFDS 与 PIL 相差 1.01，即 RLDS 重建时的重编码噪声；两者都与渲染帧差 7。

这不是格式对错的问题——字节就是字节，上游内部自洽。问题只是**两个组件对同一批字节
的解释不一致**，而这个不一致必须在三处之一被吸收：采集时转换（要重采 55 GB）、
RLDS 转换时重编码（要重训）、或评测时对齐（零成本）。

**当前的处理是评测时对齐**，`rollout.observe_task` 交换通道。这是**实验范围的权宜**，
不是设计决定：55 GB 数据和在其上训出的权重是既成事实，而过拟合闸只是健全性检查，
不值得为它把以后的路钉死。真正的修法（以及付不付那个重训）留到建正式流水线时再定，
那一行代码旁边写明了这一点。

改完后训练帧与评测帧的像素差：2.70 / 2.87 / 3.51 / 4.10（第 0/300/600/900 步），
残差是两次独立路径追踪之间的采样噪声。

## 顺带查出的：我们绕开了上游的读取器

扫描整条流水线后，规律很清楚——**写数据的路径复用上游，读数据的路径另起炉灶**：

| 我们的 | 上游已有 | 后果 |
|---|---|---|
| `panthera_rlds.py` 的图像处理 | `envs/utils/parse_hdf5.py` | 一次都没 import，通道约定就此丢失 |
| `rollout.py`（473 行） | `script/eval_policy.py`（362 行） | 环境构建、观测准备全部重写 |
| `render_rollout.py` | `envs/utils/images_to_video.py` | 上游签名里就带 `is_rgb` 参数，约定是显式的 |
| `executor.py` | `_base_task.move()` | 有正当理由：上游是阻塞式，我们需要 50 Hz 稠密零阶保持 |

采集侧是老实走上游的（`script/collect_data.py`、`pkl2hdf5`），所以数据本身遵循上游约定。
**格式的约定住在读取器里**，绕开读取器就等于丢掉约定，而且丢得无声无息。

`render_rollout.py` 已改用上游的 `images_to_video`。`rollout.py` 与 `eval_policy.py`
的重叠尚未处理。

## 闭环结果：失败模式变了，但仍未成功

用现有过拟合模型 + 修正后的相机重跑闭环（episode 2）：

| 指标 | 修相机前 | 修相机后 |
|---|---|---|
| 阶段 | 0 · 从未靠近 | **4 · 搬运到槽附近** |
| 接触 / 夹持步数 | 0 / 0 | 5014 / 5013 |
| 抬升高度 | 0 | 10.2 cm |
| 物体移动距离 | 0 | 37.8 cm |
| 物体到插槽最近距离 | 0.382 m（未动） | **0.027 m** |
| 夹爪闭合占比 | 0.0 | 0.93 |

策略会靠近、抓取、抬起、搬运到插槽附近，但**从不释放**：

```
专家   夹爪 @231 闭合，@801 重新张开
策略   夹爪 @180 闭合，之后再也没张开
       每步仍在移动（2.2–2.7 mrad），不是卡死
       前 1037 步与专家偏离中位 74.5 mrad
```

开环首块 3.9 mrad、闭环漂到 74.5 mrad，是典型的累积误差 / 协变量偏移：
单条轨迹对偏离轨迹的状态零覆盖，漂出去就回不来，因此永远到不了释放条件。

## 同时修掉的两个次要缺陷

**评测无条件做中心裁剪。** `rollout.py` 对每帧调 `center_crop_image`，而训练传的是
`--image_aug false`。上游把裁剪门控在 `cfg.center_crop`，其 docstring 明说该裁剪是
为了匹配训练时随机裁剪产生的分布。实测影响很小（852.6 vs 868.6 mrad），是真缺陷
但不是主因。现改为由 checkpoint 的观测契约决定，**无契约时不裁**。

**checkpoint 契约是死代码。** `packages/panthera_vla/checkpoint.py` 的
`write_training_record` 零调用者，`training.json` 从未产出，`gate.json` 里
`policy_contract_source` 因此是 `"command line"`。现已接入 `run_finetune.py`：
训练前后各写一次，维度与 chunk 从 `prismatic.vla.constants` 读**实际生效值**
（`ROBOT_PLATFORM` 未设时会静默回落 LIBERO，chunk 变 8、proprio 变 8），
并与 RLDS 的动作维度交叉校验；数据集根路径缺失时训练前即退出。

## 对既有结论的影响

`docs/18` 的 **0/18 与 0/12 全部作废**——它们都是在一个随机放置的相机下测的，
不能作为对策略能力的陈述。本轮 gate 2 的 0/1 同理。

专家复现的 1249/1280 **不受影响**：`replay.py` 走 `need_plan=False`，
实测规划调用 0 次；相机不影响物理。
